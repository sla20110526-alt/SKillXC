# 视频 QC 与结果回流

遵守 [轻量生产与严格记录合同](../production-router-handoff/references/interaction-modes.md)。先明确工作模式、诊断对象和证据能力，再检查结果；不加载任何大师 Profile，不提交生成任务，不替用户作“可用”决定。

## 三种工作模式

每张任务单只选择一种模式：

- `A｜即时诊断`：默认轻量模式。检查一个镜头、生成单元或用户指出的问题，直接返回可观察差异、根因层和最小返工路径；不创建或更新项目文件。
- `B｜项目复盘`：按用户指定范围汇总当前可访问的视频、截图、明确文字反馈、标准诊断摘要或正式 QCR 记录；把不可访问对象列为缺失。复盘分析默认不落盘，只有用户明确说“保存/记录本次复盘”才转严格记录。
- `C｜正式记录`：仅在用户明确说“记录本次QC”“保存失败原因”等时进入。冻结范围和授权原文，在独立记录对话写 `QCR@版本`、QC CSV、记录卡与校验报告；不借记录任务继续创作或扩大诊断范围。

普通“失败了”“这里不对”“按这个方向改”“镜头可用”“继续”都不是记录授权。用户要求项目复盘不等于授权保存复盘文件；必须另有明确“保存/记录”措辞。

## 进入门与证据能力

1. 先锁定项目、分镜组、镜头、生成单元、`VPR@版本`、`VRM@版本` 和本次结果定位；缺少文件路径不妨碍保存用户明确的“可用”结论，但视觉 QC 不能把未见内容说成已核验。
2. 只读取当前问题需要的精确期望依据：当前分镜/镜头、正式资产、表演、摄影、灯光、声音、VFX、连续性，以及本次 VPR/VRM。不得用旧版本拼出理想结果。
3. 根据证据载体限定结论：
   - 视频可检查时间变化、动作、表演、运镜、连续性和声音；无声视频不得评价声音。
   - 截图只检查该帧可见身份、构图、空间、光影、静态接触和 VFX 阶段；不得据此判定完整动作、节奏、声音或镜头稳定结束。
   - 用户明确文字反馈可据其原意给出有限路由；未提供的视觉细节标“未核验”，不得补想象。
   - 组合证据逐项说明各自覆盖范围；相互冲突时暂停根因定级，只留一个最小补证据决定点。
4. 没有唯一对象、当前版本链或足以支撑所需判断的证据时，不输出“已确认根因”；可以先给有限诊断并明确验证边界。

详细的观察分类、证据强度和唯一责任映射见 [视频QC诊断与返工合同](references/video-qc-diagnosis-contract.md)。

## 诊断顺序

1. 写证据类型、定位、可检查范围和不可检查范围。
2. 按时间点或画面范围描述可观察现象；使用“结果实际发生什么”，不先写原因。
3. 写与哪个当前期望依据不一致；没有精确期望时只描述现象，不把个人偏好冒充错误。
4. 将问题归入八类之一：人物身份与状态、表演与口型、动作与物理接触、构图与运镜、空间与光线、连续性、VFX、声音。
5. 标记严重度：
   - `阻断`：破坏人物/事件理解、正式身份、因果、物理接触、关键台词、空间方向或镜头衔接，当前结果不能用于预定位置；
   - `重要`：不阻断基本理解，但明显削弱情绪、可信度或连续性，应返修；
   - `可接受偏差`：不改变预定叙事、身份和承接，可保留给用户决定。
6. 逐层对照上游设计、VPR 正文、VRM 参考职责和生成结果，选择一个主根因层；根因判定写“已确认 / 高概率 / 待复核”并列证据。
7. 每个问题只给一个当前责任节点和一项最小修订。多个独立根因拆成多条问题；不能把同一条同时退给多个 Skill。
8. 给出复核动作：原样重试、下一 VPR/VRM 对照、上游新版本对照，或补充一项最小证据。

## 四类根因与结果回流

- `上游设计错误`：当前分镜、资产、表演、摄影、灯光、声音、VFX或生成单元设计本身与目标不符或不可执行。返回该字段唯一写入者；本 Skill 不直接修改。
- `Prompt漏译或冲突`：上游正确，但 VPR 丢失、歧义化、错误排序或互相冲突。返回 `video-prompt-production`，建立下一完整 VPR；VRM 未变则沿用。
- `参考映射或负载问题`：VRM 的来源、顺序、唯一用途、允许/禁止继承、状态匹配或负载有误。返回 `video-prompt-production`，先建立下一 VRM，再建立下一 VPR。
- `模型随机偏差`：当前上游、VPR、VRM和设置均正确，结果仍偶发未执行。返回外部人工生成节点，使用完全相同的 VPR/VRM/设置原样重试，不升级版本。只有重复同类失效显示设计超出平台稳定能力时，才改判上游生成单元/镜头设计问题。

证据不足时使用 `证据不足暂不可判定`，不强塞进四类之一，也不让“模型随机”成为默认兜底。

## 即时诊断与项目复盘输出

使用 `assets/视频QC诊断与返工模板.md`，轻量回显只包含：对象与版本、证据能力、按严重度排序的问题、主根因及判定状态、唯一返回节点、最小修订和一个下一决定点。默认不显示或写入 QC 表。

项目复盘只汇总可追溯材料，分开报告：

- 已核验问题与仍缺证据的对象；
- 各问题类别、根因层和责任节点的重复模式；
- 项目特有修订与可能通用化的规则候选。规则候选只是建议，不能自动改中央 Skill、建立项目模板 Skill 或登记失败原因。

## 正式记录

用户明确授权后，先用 `assets/视频QC记录对话激活指令模板.md` 冻结项目、范围、诊断摘要和授权原文，再在独立对话使用：

- `assets/视频QC记录模板.csv`
- `assets/video-qc.schema.json`
- `assets/视频QC记录卡模板.md`

正式记录集使用稳定 `QCR-<项目代号>-<范围代号>` 身份和 `v###` 版本。首次为 `v001`；行内容、诊断依据、根因、路由、用户结论或范围发生变化时建立完整下一版本，旧版不覆盖。问题 ID 在同一记录集内稳定；新增问题使用新 ID。

正式记录只保存已完成诊断。`用户结果结论` 必须逐字依据用户原文；用户未表态时写“未提供”，不能从 QC 严重度推断“失败”或“可用”。Schema 通过只证明结构合格，不证明根因正确、问题已修复或镜头可用。

## 与其他记录 Skill 的边界

- QC 表保存可观察问题、期望依据、根因证据、唯一责任路由和复核动作。
- `generation-version-log` 保存生成批次、Prompt/参考/设置、用户失败描述、结果采用和进度。仅当用户明确要求这类记录时另行路由；不得把 QC 授权扩张为批次记录授权。
- 用户明确说“镜头可用／成片可用”即可形成轻量结果结论，不要求上传视频；只有用户另说“同步/记录进度”时才交 `generation-version-log`。QC 不把可用镜头登记成正式资产。
- 只有用户明确要求保存 QC/失败原因时才落盘；即时分析、返修建议和用户反馈本身都不自动写文件。

## 禁止事项

- 不修改分镜、资产、表演母档、摄影/灯光/声音/VFX卡、VRM、VPR或进度表。
- 不从一张截图推断完整动作、声音或剪辑，不从文字反馈声称看过视频。
- 不把多个可能原因都写成“已确认”，不把同一问题同时退给多个责任 Skill。
- 不因 Schema 通过、AI 判断“可接受”或用户继续下一组而自行判定镜头可用。
- 不要求用户为“镜头可用”结论补传视频；但没有视觉证据时必须保持视觉核验边界。

## 输出

- 即时诊断或项目复盘：诊断与返工结果，不落盘
- 正式记录：`QCR@版本`、QC CSV、记录卡与校验报告
- 唯一责任返回节点、最小修订方向和复核动作
