# 资产状态传播规则

## 1. 三种版本关系

- `生产依据父资产ID与版本`：该文件实际由哪个父版本制作；登记后永久保留，不因兼容确认改写。
- `生产依据附加资产ID与版本`：持物、穿戴、场景光影、交互组合等实际生成时使用的其他正式版本；永久保留。
- `当前兼容依赖资产ID与版本`：该版本当前已被用户确认可与哪些上游版本继续组合。首次登记等于全部生产依据；只有用户明确确认兼容后才能替换其中的旧版本。

所有依赖引用使用 `正式资产ID@版本`；多个值使用中文分号 `；`，没有依赖写“不适用”。禁止只写资产 ID、资产名或“最新版”。

## 2. 传播触发

只有专用登记对话执行以下动作时传播：

1. 同一正式资产 ID 登记新的当前版本。
2. 用户明确确认某个待复核版本兼容新的依赖版本。

候选生成、生产返修、用户调整方向或失败结果都不改变正式数据状态。

## 3. 新版本登记算法

1. 以被替代的 `正式资产ID@旧版本` 为起点。
2. 扫描同项目全部正式/可调用版本；凡“当前兼容依赖”含起点者，是直接受影响版本。
3. 将直接受影响版本标为 `待复核`，再以它们各自的 `正式资产ID@版本` 继续扫描，直到没有新的传递依赖者。
4. 不传播到其他项目、不传播到仅共享名称但没有版本依赖的资产、不自动改变声音身份卡或其他创作控制卡。
5. 新登记版本写 `可调用`；同 ID 旧版本写 `历史`；派生版本写 `待复核`。三种变化分别写传播行。
6. 依据关联场次和资产状态传播表，列出场次就绪、生成单元、分镜和正式 Prompt 的复核范围；不直接改写这些下游数据。

## 4. 典型关系

- 人物基础卡换版：传播至服装/妆造、伤口/雨湿/战损、人物—道具交互组合，以及依赖这些版本的下游组合。
- 服装版本换版：传播至基于该服装制作的伤口、污迹、战损、持物和交互组合；不传播到人物基础卡。
- 道具换版：传播至引用该道具版本的持物/交互组合；不自动使人物基础卡失效。
- 场景母图换版：传播至基于旧母图的场景视图与光影状态，再传递至依赖这些视图/光影的组合资产。
- 独立声音资产换版：旧音频历史、新音频可调用；场戏声音卡与正式 Prompt 进入下游复核，但声音身份卡不因音频换版自动升级。

## 5. 解除门

- `待复核` 不是失败，也不等于必须重做；它表示原版本不能继续默认为可调用。
- 专业比较结论不等于用户授权。只有用户明确指向唯一版本并确认继续使用，登记对话才能把对应兼容依赖更新到新版本；全部当前依赖均可调用时才恢复可调用。多个上游同时换版时可以逐项确认，未全部完成前保持待复核。
- 传递传播可能使末端资产在自身直接依赖没有换号时进入待复核。例如 `CHR@v001 -> COSTUME@v001 -> STATE@v001` 中，人物换版会使状态版暂停；服装版确认兼容后，状态版复核的是仍为 `COSTUME@v001` 的直接依赖，不得把新的 `CHR` 版本塞进状态版的当前兼容依赖。
- 每次确认只关闭与该资产、该依赖路径相符的旧待复核事件；旧事件保留历史状态变化，但 `传播处理状态` 更新为 `已复核继续`。本次确认另追加事件。仍有其他未解决依赖时资产保持待复核，本次确认事件本身仍记为已经处理。
- 用户确认重做不登记新结果；新结果仍走正常登记门。
- 恢复前检查它依赖的全部版本当前均可调用；存在任何待复核、停用或历史依赖时保持待复核。

## 6. 原子性和回滚

正式资产登记表、可调用资产表和资产状态传播表是一个写入事务。先在三份临时完整表中应用登记与传播，完成单表 Schema 和跨表业务检查，再备份并替换。写后复检失败则恢复三张旧表；不得留下“正式表已改、可调用表未改”或传播记录缺失的状态。

事务由 `../scripts/update_asset_registry.py` 执行。登记使用 `../assets/正式资产登记操作模板.json`，确认兼容使用 `../assets/待复核兼容确认操作模板.json`；不得手工分次覆盖三张表。
