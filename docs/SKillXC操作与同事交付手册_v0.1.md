# SKillXC 操作与同事离线交付手册 v0.1（详细版）

适用范围：已有剧本或生产内容明确的真人写实项目；GPT Image 2 制作图片资产；Seedance 2.0 由用户在外部平台人工生成；终点为正式镜头 Prompt 与用户确认的可用镜头。

系统状态：结构化 Beta。系统结构、30 个 Skill、数据合同和交接规则已经建立；尚需通过 V01 真实项目端到端验证，才能称为“真人写实第一版生产闭环已验证”。

本手册供制片、导演、AI 影视制作人员、数据记录人员和系统管理员使用。它解释“什么时候开新对话、怎样激活、怎样返回、怎样离线交给同事”，不替代各 Skill 的专业规则。发生冲突时，以用户最新明确指令、项目当前有效数据、`production-router-handoff` 和唯一责任 Skill 为准。

## 1. 先记住四条总原则

1. 不按“每问一句”开新对话，按“责任和对象”开新对话。
2. 生产控制/严格记录对话与创作生产对话分开，尤其不能在创作对话直接写正式登记、控制索引、进度或正式 QC。
3. 每个项目必须有一个长期保留的“项目总控与路由”对话；后续新对话由它或当前上游对话生成短交接包。
4. 同事不需要访问中央开发仓库。系统维护者把当前成熟版本制作成冻结的离线发行包，同事复制并安装该发行包即可。

推荐的新对话单位是：

`同一项目 + 同一责任 Skill + 同一对象/场次范围 + 同一种写入权限`

## 2. 本手册中的新对话标记

后续每一步都使用以下标记：

- `【新对话：必须】`：不能留在原对话执行。第一次进入时建立专用对话；以后遇到同一职责时返回这个既有对话。
- `【新对话：建议】`：技术上可以继续，但为避免上下文污染，正式项目建议新建。
- `【新对话：可选】`：只有出现对应需求时才建立。
- `【继续当前对话】`：责任 Skill、对象范围和写入权限都没有改变，不要另开。
- `【返回既有对话】`：不要再创建同名新对话，回到前面已经建立的指定对话继续。
- `【外部人工节点】`：离开 Codex，在 GPT Image 2 或 Seedance 2.0 操作；不为平台操作单独建立 Codex 对话。

### 2.1 判断口诀

出现下列任一变化，原则上新开或切换专用对话：

- 项目变了；
- 唯一责任 Skill 变了；
- 从一个人物、场景、道具或场次切换到另一个独立对象；
- 从创作生产变为正式登记、版本生效、进度记录、正式审计或正式 QC；
- 需要交给另一名同事；
- 原对话已混入大量失败候选、旧版本或无关内容。

以下情况通常留在原对话：

- 同一人物候选反复修改；
- 同一人物从基础版进入服装或剧情状态变体；
- 同一场景母图补空间圣经、预制视图或状态变体；
- 同一分镜表吸收剪辑或摄影审核意见；
- 同一生成单元只修改 Prompt 表达；
- 完全相同输入原样重试。

## 3. 每个项目应建立的对话结构

### 3.1 项目总控对话

`【新对话：必须｜每个项目只建一次】`

建议名称：`【项目ID】-00-项目总控与路由`

唯一责任 Skill：`production-router-handoff`

只负责：

- 核对项目绑定和当前阶段；
- 确定下一唯一责任 Skill；
- 建立后台完整任务单；
- 输出新对话短交接包和激活指令；
- 接收专业对话返回结果；
- 判断继续、返工或进入下一阶段。

不负责：直接设计资产、写分镜、装配 Prompt、登记资产或写正式记录。

首次激活示例：

```text
使用 $production-router-handoff。我要启动一个已有剧本或生产内容明确的真人写实项目。
项目名称：【填写】
建议项目ID：【填写；没有时请提出】
项目数据根目录：【绝对路径；没有时先提醒我建立】
剧本或生产内容：【附件或路径】
先核对项目绑定、当前阶段和下一唯一责任Skill。未经我确认，不要加载其他SKillXC Skill或任何Profile。
以后需要切换对话时，请给出：建议对话名、短交接包、可复制的激活指令和完成后的返回位置。
```

### 3.2 五类长期严格记录对话

这些对话不必在项目第一天全部建立。第一次真正需要该写入动作时建立，以后返回原对话复用。

| 对话 | 新建规则 | 唯一责任 Skill | 只负责 |
|---|---|---|---|
| `【项目ID】-01-项目绑定与资产登记` | `【新对话：必须｜首次绑定时建立】` | `approval-asset-registry` | 项目绑定、正式资产登记、可调用映射、待复核解除、状态传播和回执 |
| `【项目ID】-02-创作控制版本` | `【新对话：必须｜首张长期控制卡生效时建立】` | `creative-control-versioning` | 风格四卡、表演母档、声音身份卡的版本和生效事务 |
| `【项目ID】-03-生成与进度记录` | `【新对话：必须｜用户首次明确要求同步或保存批次时建立】` | `generation-version-log` | Prompt/结果进度、生成批次、输入设置和用户失败描述 |
| `【项目ID】-04-正式审计记录` | `【新对话：必须｜用户首次明确要求保存审计时建立】` | `continuity-readiness-audit` | 保存正式连续性/就绪审计 |
| `【项目ID】-05-正式QC记录` | `【新对话：必须｜用户首次明确要求保存QC时建立】` | `video-qc-review` | 保存 QCR 根因、证据边界和返工路由 |

生成记录与正式 QC 分开授权。前者保存“用什么生成、用户报告了什么”，后者保存“证据支持的主根因和唯一返工责任”。

### 3.3 创作生产对话

创作生产对话按专业责任和对象建立：

- 风格阶段：项目风格总控、美术、全片摄影、项目灯光；
- 资产阶段：一个人物、场景、道具/载具、生物/怪物或 VFX 对象一个生产对话；
- 图片 Prompt：一个对象或一个清晰批次一个图片 Prompt 对话；
- 场戏阶段：按场次/场次组分别建立剧作、导演调度、场戏表演、场戏摄影、镜头设计、剪辑、声音和视频 Prompt 对话；
- 即时 QC：需要独立诊断时按镜头组建立，可不落盘。

大师 Profile 不是项目中的独立生产对话。导演、摄影、美术、剧作和剪辑 Profile 都在对应责任 Skill 的允许阶段内询问并加载；阶段交付后关闭本体，下游只接收已经转译的项目规则。只有维护 Profile 资料库本身时，才另开系统维护对话。

### 3.4 对话不是项目数据库

每个项目必须有独立的数据根目录和项目数据绑定卡，不能把项目数据写入 SKillXC 系统文件，也不能与其他项目共用表格。

- Markdown 卡片供人确认范围、结论、缺口和交接；
- CSV 保存多行权威记录；
- JSON Schema 检查表头和逐行结构；
- 数据校验报告写在对应项目数据目录；
- 对话只读取当前任务所需的最小切片，不是唯一数据源。

结构检查通过不等于创作批准、正式登记、Prompt 放行或镜头可用。

## 4. 新对话的标准交接方法

### 4.1 除首次总控外，不要裸启动专业对话

不要只发送“使用摄影 Skill”“帮我做人物”或把整个旧聊天复制过去。先在项目总控或当前上游对话发送：

```text
请为下一步建立完整任务单和短交接包，并明确：
1. 是否需要新对话；
2. 建议对话名称；
3. 唯一责任Skill；
4. 完整任务单路径；
5. 允许读取的最小数据切片；
6. 可直接复制到新对话的激活指令；
7. 完成后应返回哪个既有对话。
```

### 4.2 短交接包必须包含

```text
项目ID：
任务ID@任务单版本：
当前阶段：
唯一责任Skill：
完整任务单路径：
当前唯一目标：
最小数据切片（名称｜精确ID@版本｜项目内路径）：
用户尚需决定：无 / 一个明确决定点
禁止事项：
返回条件：
```

### 4.3 通用新对话激活模板

```text
使用 $【唯一责任Skill】，只处理【任务ID@任务单版本】的当前唯一目标。
先读取【完整任务单路径】，随后只读取短交接包列出的最小数据切片。
不要加载其他SKillXC Skill或任何未列明Profile；不要切换项目、重拆剧本、修改预留资产ID或自行登记。
默认使用轻量生产模式，只向我显示本轮结果、必要缺口和一个确认点。
如果需要扩大范围，停止并返回 $production-router-handoff。
完成后按短交接包的返回条件交回【目标对话名】。

【在这里粘贴短交接包】
```

### 4.4 完成专业任务后怎样返回

在专业对话发送：

```text
请按当前任务的返回条件生成返回包。只列成果ID@版本、成果路径、状态、未解决缺口、下游最小切片和应返回的对话名称；不要展开整个项目数据。
```

然后回到项目总控或短包指定的既有对话，粘贴返回包。不要在新建的第三个对话中转述。

## 5. 真人写实生产流程：逐步骤对话说明

以下步骤从安装到可用镜头结束。没有对应需求的可选分支可以跳过，但不能跳过项目绑定、正式版本、登记触发、就绪门和 Prompt/镜头状态分离。

### 步骤 00｜离线安装系统文件

`【不属于项目生产对话】`

由系统管理员按本手册第 9 节，把离线发行包安装到同事电脑。安装完成前不要开始真实项目。

### 步骤 01｜安装后的运行时验收

`【新对话：必须｜每台电脑、每次完整升级后各做一次】`

建议名称：`SKillXC-安装验收-日期`

激活示例：

```text
请使用 $production-router-handoff 做安装验收。这里只验证SKill是否可发现，不建立项目、不创建项目数据，也不调用其他专业Skill。
请先告诉我：是否识别到生产总路由、当前可发现的SKillXC Skill数量，以及其余专业Skill是否保持“需用户确认后显式调用”。
```

通过标准：识别到 30 个 Skill；总路由可用；其余 29 个不被自动批量加载。

### 步骤 02｜建立项目总控

`【新对话：必须｜每个项目一次】`

建立 `【项目ID】-00-项目总控与路由`，使用第 3.1 节首次激活示例。此后项目暂停、换人、恢复、上游返工或不确定下一步时，都回到该对话。

### 步骤 03｜绑定项目数据目录

`【新对话：必须｜首次建立；以后返回既有登记对话】`

建议名称：`【项目ID】-01-项目绑定与资产登记`

从哪里取得短包：项目总控对话。

激活示例：

```text
使用 $approval-asset-registry，工作模式=项目绑定。
只读取短交接包指定的项目ID、项目数据根目录和绑定任务单。
建立待确认绑定卡；得到我的明确确认后再初始化必要索引。
不要生产资产、不要修改剧本、不要登记任何候选。
完成后返回【项目ID】-00-项目总控与路由。

【粘贴项目绑定短交接包】
```

完成信号：返回 `项目数据绑定卡.md` 的路径、版本和确认状态。

### 步骤 04｜锁定项目类别与生产边界

`【新对话：必须｜每个项目初次锁定一次；实质变更时建立下一任务版本】`

建议名称：`【项目ID】-10-类别锁定`

唯一责任 Skill：`project-category-lock`

激活示例：

```text
使用 $project-category-lock，只处理当前项目的类别和生产边界锁定。
通过问答和我提供的参考图确认：真人写实程度、画幅、GPT Image 2图片资产、Seedance 2.0外部人工视频节点及参考用途。
不拆资产、不设计风格、不调用Profile。完成后返回项目总控。

【粘贴短交接包】
```

如果用户上传参考图，由本对话判断类别；类别没有锁定前不进入批量资产生产。

### 步骤 05｜建立剧本事实索引

`【新对话：必须｜剧本内容版本改变时回到该既有对话建立下一版本】`

建议名称：`【项目ID】-11-剧本事实索引`

唯一责任 Skill：`script-truth-index`

激活示例：

```text
使用 $script-truth-index，只读取项目锁定卡和本任务指定的剧本内容版本。
建立可追溯的场次、人物、原台词、事件、状态、道具流转、声音和连续性事实索引。
不得创作性补全或改写剧本。完成后返回项目总控。

【粘贴短交接包】
```

### 步骤 06｜资产拆解与预留正式 ID

`【新对话：必须】`

建议名称：`【项目ID】-12-资产拆解`

唯一责任 Skill：`script-asset-breakdown`

激活示例：

```text
使用 $script-asset-breakdown，只按当前剧本事实索引拆解人物、服装、场景、光影、道具/载具、生物/怪物、VFX、图案文字和必要声音候选。
为正式资产槽位预留稳定ID，但不得分配正式版本、不得把候选写成已登记资产。
完成后返回项目总控。

【粘贴短交接包】
```

预留 ID 不是正式资产。正式版本只在用户明确登记后产生。

### 步骤 07｜资产需求、依赖和批次计划

`【新对话：必须】`

建议名称：`【项目ID】-13-资产需求计划`

唯一责任 Skill：`asset-demand-plan`

激活示例：

```text
使用 $asset-demand-plan，把当前资产拆解结果转成需求槽位、父子依赖、优先级、生产批次和场次就绪条件。
不生产候选、不写图片Prompt、不登记资产。完成后返回项目总控。

【粘贴短交接包】
```

### 步骤 08｜专业事实顾问分支

`【新对话：可选｜任何阶段出现专业事实缺口时建立】`

建议名称：`【项目ID】-顾问-问题简称`

唯一责任 Skill：`specialist-consultant-router`

激活示例：

```text
使用 $specialist-consultant-router，只处理短包中的一个专业问题。
先判断它属于“必须准确、允许艺术化、纯虚构规则”哪一类，再确定唯一主专业领域。
没有可靠证据时保持“暂不可裁决”；不要把推测写成项目事实。完成后返回短包指定的上游对话。

【粘贴短交接包】
```

同一批次有多个互不相干的问题，应分别建任务；不要在一个顾问对话里同时扮演多个无关专家。

### 步骤 09｜建立风格锁定总控

`【新对话：必须】`

建议名称：`【项目ID】-20-风格锁定总控`

唯一责任 Skill：`style-lock-director`

风格阶段的实际执行顺序是：

`步骤09项目风格意图 → 步骤13确认生效 → 步骤10美术 → 步骤13确认生效 → 步骤11摄影 → 步骤13确认生效 → 步骤12灯光 → 步骤13确认生效 → 步骤14 P0`

激活示例：

```text
使用 $style-lock-director，先建立项目风格意图任务和四卡依赖计划。
本对话只统筹“项目风格→美术→摄影→灯光→P0测试→组合快照”，不替各专业Skill写专业卡，不批量加载Profile。
到每个专业阶段时，先给我新对话名称、短交接包和激活指令。完成当前风格意图后等待我确认。

【粘贴短交接包】
```

导演 Profile 只在项目风格意图阶段询问本次是否加载；不能自动延续到场戏调度阶段。

项目风格意图草案确认后，先进入步骤 13 的既有“创作控制版本”对话确认生效，再开始美术基线。不要把未生效草案直接交给美术。

### 步骤 10｜美术与 LookDev 长期基线

`【新对话：必须】`

建议名称：`【项目ID】-21-美术LookDev`

唯一责任 Skill：`art-lookdev-direction`

激活示例：

```text
使用 $art-lookdev-direction，工作模式=项目LookDev长期基线。
只读取已确认的项目风格意图和短包列出的剧本/顾问最小切片。
先询问我是否从资料库选择美术Profile；未确认不得读取完整Profile。
只决定物质世界、建筑陈设、服装妆造、道具、材质工艺、老化、固有色和视觉母题，不决定摄影机和光源。
完成草案后返回风格锁定总控。

【粘贴短交接包】
```

美术基线草案确认后，先进入步骤 13 确认生效，再开始全片摄影基线。

### 步骤 11｜全片摄影基线

`【新对话：必须】`

建议名称：`【项目ID】-22-全片摄影基线`

唯一责任 Skill：`cinematography-direction`

激活示例：

```text
使用 $cinematography-direction，工作模式=全片摄影基线。
只读取当前美术LookDev基线及短包列出的最小切片。
先询问我是否选择摄影指导Profile；这是本项目常规询问摄影Profile的唯一阶段。
建立画幅、镜头语言、焦段倾向、机位距离、景深、曝光保护、摄影机运动和例外边界，不写逐镜分镜。
完成草案后返回风格锁定总控。

【粘贴短交接包】
```

场戏摄影、逐镜摄影审核和 Prompt 阶段继承摄影规则卡，不重新加载完整摄影 Profile。

全片摄影基线草案确认后，先进入步骤 13 确认生效，再开始项目灯光基线。

### 步骤 12｜项目灯光基线

`【新对话：必须】`

建议名称：`【项目ID】-23-项目灯光基线`

唯一责任 Skill：`lighting-direction`

激活示例：

```text
使用 $lighting-direction，工作模式=项目灯光长期基线。
只读取全片摄影基线及短包列出的最小切片，不读取大师Profile。
建立光源角色、方向逻辑、反差、负补光、反射、人物受光和多视图继承边界；不改变摄影机、空间结构或VFX本体。
完成草案后返回风格锁定总控。

【粘贴短交接包】
```

项目灯光基线草案确认后，进入步骤 13 确认生效；四张卡都生效后才能执行 P0 风格测试。

### 步骤 13｜风格四卡逐张确认生效

`【新对话：必须｜首次建立；以后返回既有“创作控制版本”对话】`

建议名称：`【项目ID】-02-创作控制版本`

唯一责任 Skill：`creative-control-versioning`

每张长期卡的专业内容仍由原专业对话生产。本对话只执行版本入表、用户确认生效、旧版替代或停用。它不是等四张卡全部写完后才执行一次，而是按以下顺序重复使用同一个控制版本对话：

`项目风格草案 → 确认生效 → 美术草案 → 确认生效 → 摄影草案 → 确认生效 → 灯光草案 → 确认生效`

激活示例：

```text
使用 $creative-control-versioning，只执行短包指定的项目创作控制卡版本事务。
核对项目ID、来源专业Skill、卡片ID@版本、中央源/Profile精确引用和我的确认原文。
不要修改卡片创作内容，不要版本化资产、分镜、Prompt或普通场戏短卡。
完成后返回【项目ID】-20-风格锁定总控。

【粘贴创作控制版本操作短包】
```

四卡依赖固定为：项目风格无上游；美术只直接引用项目风格；摄影只直接引用美术；灯光只直接引用摄影。

### 步骤 14｜P0 风格测试与批量放行

`【返回既有对话：项目风格锁定总控】`

风格总控为每个 P0 命题建立测试任务。P0 必须绑定已有需求槽位、预留正式资产 ID、唯一责任资产 Skill 和单一测试命题。

随后按步骤 15—18 进入相应资产设计、图片 Prompt、外部生成、责任资产验收和明确登记流程。P0 图片通过不自动登记；登记也不自动代表全部 P0 通过。

完成每个测试后：

`【返回既有对话：项目风格锁定总控】`

由风格总控完成评审、四卡冲突门、组合快照和批量生产放行。

## 6. 资产生产循环：逐步骤对话说明

通用激活结尾：

```text
只读取短交接包列出的正式父资产、附加资产、风格包和当前需求槽位。
先完成本资产生产卡和候选验收标准；图片Prompt另交 $image-prompt-production。
失败候选不登记，普通认可不登记，只有我的明确登记措辞才生成登记申请。
完成当前设计后返回项目总控或短包指定对话。

【粘贴短交接包】
```

如果资产身份混合、类别不清或生产顺序冲突：

`【新对话：可选】`建立 `【项目ID】-世界资产路由-需求简称`，使用 `$world-asset-production`。它只拆分身份、依赖和责任 Skill，不设计候选。

```text
使用 $world-asset-production，只处理短包中类别不清或混合的资产需求。
拆分可复用资产身份、唯一责任Skill、父子依赖和生产顺序；不设计资产、不写图片Prompt、不生成候选、不登记。
完成后返回资产需求计划或项目总控。

【粘贴短交接包】
```

### 步骤 16｜装配 GPT Image 2 图片 Prompt

`【新对话：必须｜每个资产对象或清晰图片批次第一次进入时】`

建议名称：`【项目ID】-对象名-图片Prompt`

唯一责任 Skill：`image-prompt-production`

从哪里取得短包：对应资产责任生产对话。

激活示例：

```text
使用 $image-prompt-production，只把当前责任资产Skill已经确认的生产卡、精确父版本、参考映射和继承约束装配成GPT Image 2 Prompt。
图片工作模式=【新生成/参考编辑】；图片PromptID@版本=【填写】。
不重新设计资产、不登记候选、不默认记录失败。完成后把Prompt和结果回流要求交回【对应资产责任对话名】。

【粘贴短交接包】
```

同一对象 Prompt 表达返修：`【返回既有对话：该对象图片Prompt】`。只有正文、参考映射、平台设置或上游版本发生可复现变化时升级 Prompt 版本；完全相同输入原样重跑不升级。

### 步骤 17｜在 GPT Image 2 外部生图

`【外部人工节点】`

用户把 Prompt 和参考素材复制到 GPT Image 2。生成结果返回步骤 15 的资产责任对话复核，不直接送登记对话。

### 步骤 18｜资产候选复核与返修

`【返回既有对话：对应资产责任生产对话】`

- 候选失败：说明调整方向，继续在资产对话修设计；需要改 Prompt 时返回既有图片 Prompt 对话。
- 用户提供新参考：先由资产责任 Skill 判断是否改变身份、父版本或设计边界，再决定继续或建立下一任务版本。
- 用户只说“可以、不错、继续、按这个改”：不登记。
- 用户希望记录失败原因：先让当前对话生成记录同步包，再进入步骤 34 的严格记录对话。

### 步骤 19｜正式登记资产

`【返回既有对话：项目绑定与资产登记】`

如果该项目还没有登记对话，则 `【新对话：必须】`建立 `【项目ID】-01-项目绑定与资产登记`。

触发条件只有明确措辞，例如：

- “登记这张”；
- “确认登记这张人物五视图”；
- “登记这段声音”；
- 其他同时说明对象和动作的无歧义登记指令。

资产责任对话先生成登记申请和短激活指令，再复制到登记对话：

```text
使用 $approval-asset-registry，工作模式=正式资产登记。
只读取指定项目绑定卡和本次登记申请，核对预留正式资产ID、用户指定资产名、唯一候选、父版本、用途和我的登记原文。
只执行核验、正式写表、可调用映射、状态传播和登记回执；不得继续资产创作或修改候选。
完成后返回【对应资产责任对话名】。

【粘贴登记申请短包】
```

登记后：`【返回既有对话：对应资产责任生产对话】`，把登记回执交回，才能进入五视图、服装、状态、组合或其他依赖父版本的下一层生产。

### 步骤 20｜人物资产的推荐循环

`【继续/返回同一人物资产对话，不按每个版本另建】`

顺序为：

1. 选脸与脸母图 → 图片 Prompt → 外部生成 → 人物对话验收 → 明确登记；
2. 读取已登记脸母图 → 单张五视图总览卡 → 验收 → 明确登记；
3. 读取正确父人物版本 → 服装妆造版本或剧情状态版本 → 验收 → 明确登记；
4. 人物—道具交互必须同时读取已登记人物和已登记道具版本。

五视图总览卡布局：左三分之一为正面特写和 3/4 视角侧面特写；右三分之二为正面全身、侧面全身、背面全身。人物资产画幅按卡片排版需要确定，不强制跟随项目画幅。

### 步骤 21｜场景资产的推荐循环

`【继续/返回同一场景资产对话】`

顺序为：

1. 默认 3/4 斜角空间母图；只有用户明确要求时才使用剧照式母图；
2. 母图确认并登记；
3. 建立空间圣经、坐标、门窗/家具/道路/山树等锚点及投影关系；
4. 生产预制剧情视图、专项 SV3 视图、场景状态和光影状态；
5. 每张正式图片分别走图片 Prompt、验收和明确登记；空间圣经和锚点表不是图片资产。

场景光源地图另由 `lighting-direction` 生产：

`【新对话：建议｜每个重要场景第一次建立光源地图时】`

建议名称：`【项目ID】-场景名-灯光`

```text
使用 $lighting-direction，工作模式=场景光源地图。
只读取当前项目灯光基线、已确认空间圣经/锚点和本场景光影状态。
不要改变场景结构或摄影机。完成后返回场景资产对话和项目总控。

【粘贴短交接包】
```


`【外部人工节点】`

- “镜头可用/成片可用”：才表示生成结果可用；
- 镜头可用不要求用户上传视频；
- 完全相同输入原样重试不升级版本。

### 步骤 36｜生成结果反馈与即时 QC

#### 用户已经知道修改方向

`【返回既有对话】`

- Prompt 漏写或表达问题 → 返回该视频 Prompt 对话；
- 参考顺序、用途或负载问题 → 返回视频 Prompt 对话，先修 VRM；
- 构图、景别、机位、运镜问题 → 返回镜头视觉设计；
- 人物走位、遮挡、权力空间或轴线问题 → 返回导演调度；
- 表演僵硬、夸张、缺反应 → 返回场戏表演；
- 空间结构问题 → 返回场景资产；
- 灯光实现问题 → 返回场景/场戏灯光；
- 模型随机偏差 → 外部原样重试。

#### 需要系统判断根因

`【新对话：可选｜建议与Prompt生产分开】`

建议名称：`【项目ID】-生成单元ID-即时QC`

```text

依据我提供的视频、截图或明确文字反馈，先声明能核验和不能核验的范围，再定位可观察差异、主根因层、唯一责任节点和最小复核动作。

【粘贴短交接包与证据定位】
```

即时 QC 默认不落盘。诊断完成后按唯一责任节点返回已有生产对话。

```text
核对项目绑定、分镜/镜头/生成单元、VPR/VRM版本、Prompt放行状态、用户镜头结论和用户授权原文。
不要保存正式QC根因，不要把Prompt放行写成镜头可用。

【粘贴同步包】
```

#### 保存正式 QC

只有用户明确说“保存本次QC/记录失败根因”时：

`【返回既有对话：正式QC记录；没有时新建必须】`

```text
使用 $video-qc-review，工作模式=正式记录。
只按本次授权保存QCR、证据边界、主根因层、唯一责任节点和返工路由。
```

## 9. 不共享仓库时，交给同事什么

### 9.1 正确方式：制作冻结的离线发行包

系统维护者保留中央开发目录和版本历史，不给同事仓库访问权限。每次准备发给同事时，复制一份当前验证通过的文件，压缩成只读发行包，例如：

```text
SKillXC-TeamRuntime-v0.1.0-20260814.zip
```

同事拿到的是一个明确版本的运行包，不是开发仓库，也不会自动获得后续更新。

### 9.2 普通使用者必须收到的文件

离线发行包建议结构：

```text
SKillXC-TeamRuntime-v0.1.0/
├─ 00-先读手册/
│  ├─ SKillXC操作与同事交付手册_v0.1.md
│  ├─ 真人写实AI影视生产总流程_v0.1.md
│  ├─ Skill清单与交接矩阵_v0.1.md
│  └─ 发行版本说明.md
└─ skills/
   ├─ production-router-handoff/
   ├─ approval-asset-registry/
   ├─ ...
   └─ 其余全部Skill目录（合计30个）
```

必须完整复制整个 `skills/`。每个 Skill 目录中的 `SKILL.md`、`assets/`、`references/`、`scripts/` 都属于运行内容，不能只复制 30 个 `SKILL.md`。

### 9.3 普通同事不要收到的内容

默认不放入离线运行包：

- `.git/` 和任何提交历史；
- `.codex-plugin/plugin.json`，因为离线包采用直接 Skill 发现，不需要插件入口，也避免暴露仓库元数据；
- 中央维护用 `AGENTS.md`；它包含维护者目录和开发安装拓扑，不适合同事电脑；
- `deployment/windows/` 个人恢复工具和个人安装清单；
- `docs/Codex用户级Skill重装恢复.md`；
- `docs/剩余工作与完成验收总表_v0.1.md`；
- 维护者的整个 `006-skills` 目录；
- 个人插件、个人 Skill、账号、API 密钥、缓存和历史聊天；
- 任何真实项目数据、未授权素材或其他项目登记表。

### 9.4 发行版本说明模板

每个压缩包都附一份 `发行版本说明.md`：

```text
# SKillXC 离线发行版本说明

发行包版本：
制作日期：
系统状态：结构化Beta / 已验证正式版
包含Skill数量：30
适用范围：真人写实；GPT Image 2；Seedance 2.0外部人工节点
操作手册版本：
总流程版本：
已通过检查：
已知限制：
替代的上一发行包版本：
是否允许用于正式项目：
系统维护负责人：
问题反馈方式：
```

不要使用“最新版”作为包名。每位同事必须能说清当前安装的是哪个发行包版本。

### 9.5 每个具体项目另给同事的项目启动包

系统运行包和项目数据必须分开。项目启动包至少包含：

- 剧本或明确生产内容；
- 项目名称和项目 ID；
- 该项目独立的数据根目录；
- 类别方向或参考图；
- 已知历史、职业和技术事实资料；
- 允许使用的模型、平台和账号权限；
- 用户/审批负责人名单；
- 素材来源和使用授权；
- 保密、备份和交付要求。

一个同事可以安装一份 SKillXC 运行包并参与多个项目，但每个项目必须使用独立数据目录、项目绑定卡和项目对话组。

## 10. 同事电脑的离线安装与升级

### 10.0 使用前提

同事电脑至少需要：

- 已安装并登录 Codex Desktop；
- 可运行 Python 3，用于项目数据、Schema和事务脚本检查；
- 有权使用 GPT Image 2 和 Seedance 2.0；
- 有独立可写的项目数据和素材目录；
- 明确的项目审批负责人；
- 不共享维护者的 Codex 登录、模型账号、API 密钥或个人素材目录。

离线运行不要求同事安装 Git，也不要求他们知道中央开发目录的位置。

### 10.1 推荐安装方式

1. 把离线发行包解压到稳定且不会随意移动的位置，例如 `D:\SKillXC-TeamRuntime\v0.1.0\`。
2. 由管理员把该版本 `skills/` 下的 30 个 Skill 目录分别接入 `%USERPROFILE%\.agents\skills\`。
3. 推荐使用目录链接，让运行入口指向冻结发行包；不要同时再安装同名插件版本。
4. 完全退出并重启 Codex Desktop。
5. 按步骤 01 新建安装验收对话。
6. 验收通过后再创建真实项目。

如果团队成员不熟悉 Windows 目录链接，应由一名管理员统一安装。当前个人恢复脚本不能直接给同事使用；团队一键离线安装器应作为后续独立部署工具制作。

少量电脑也可以采用简化方式：把发行包 `skills/` 下面的 30 个完整目录直接复制到 `%USERPROFILE%\.agents\skills\`。这种方式仍必须整套复制、整套验收和整套更新，不能只复制 `SKILL.md`，也不能与同名目录链接或插件安装并存。

### 10.2 更新方式

系统维护者发布成熟更新时：

1. 生成新的完整离线发行包，不零散发送几个修改文件；
2. 同事退出 Codex；
3. 新包解压到新的版本目录，不覆盖旧包；
4. 管理员把 30 个运行入口统一切换到新版本；
5. 重启 Codex并重新做安装验收；
6. 新项目默认使用新发行包；
7. 正在生产的项目是否升级，由项目总控建立兼容复核任务，不能静默替换；
8. 确认新版本稳定后再归档旧包，保留至少一个可回退版本。

禁止同一台电脑混用不同发行包中的 Skill。例如 20 个来自 v0.1.0、10 个来自 v0.1.1，会造成合同和模板不一致。

### 10.3 发包前检查

系统维护者每次交付前至少检查：

- `skills/` 正好包含 30 个目录，每个目录都有 `SKILL.md`；
- Skill 内引用的 `assets/`、`references/` 和 `scripts/` 没有漏复制；
- 三份操作文档可以正常打开，编码为 UTF-8；
- 包内没有 `.git`、个人恢复工具、账号密钥、缓存、历史聊天或真实项目数据；
- `发行版本说明.md` 已填写版本、日期、已知限制和验收结果；
- 在一台未安装旧版 SKillXC 的测试环境完成步骤 01 运行时验收。

### 10.4 同事反馈给系统维护者的内容

同事不直接修改中央 Skill。发现问题时提交：

```text
发行包版本：
项目ID：
当前阶段：
责任Skill：
任务ID@版本：
问题现象：
预期结果：
实际结果：
是否阻断生产：
相关短交接包/成果ID@版本：
用户是否授权提供相关素材：
建议改进（可空）：
```

系统维护者判断它属于项目特例、通用 Skill 候选、模板缺口还是模型能力边界，再决定是否进入中央系统更新。

## 11. 团队角色与权限建议

| 角色 | 建议权限 |
|---|---|
| 系统维护者 | 维护中央系统、验证、制作离线发行包和发布更新 |
| 安装管理员 | 安装冻结发行包、核验30个Skill和执行版本切换，不修改Skill内容 |
| 项目总控/制片 | 建项目、批准阶段、维护总控对话和分配任务 |
| 创作负责人 | 在指定专业对话生产候选和交接包，不写权威登记表 |
| 资产登记员 | 只按明确登记申请写正式资产、可调用表和回执 |
| 数据记录员 | 只按授权写控制版本、进度、生成批次、审计或 QC 记录 |
| 最终审批人 | 决定登记、Prompt 放行、镜头可用和项目采用 |

小团队可以一人兼任多个角色，但仍要使用不同对话和不同写入模式，不能因为是同一人就跳过授权边界。

## 12. 常见错误

- 没有项目总控，专业对话自行决定下一阶段；
- 新建专业对话时没有任务单和短交接包；
- 每个小修改都开一个新对话，导致同一对象上下文碎裂；
- 整个项目只用一个对话，导致责任和版本混杂；
- 在资产设计对话直接登记；
- 在 Prompt 对话重新导演、重新选 Profile 或修改分镜；
- 把“继续”当成登记、Prompt 放行或镜头可用；
- 把失败候选登记成正式资产；
- 剪辑或摄影审核直接改分镜表；
- 只凭截图判断完整动作、声音或运镜；
- 把结构校验通过写成创作质量通过；
- 只复制 `SKILL.md`，遗漏 Skill 内的模板、参考和脚本；
- 把中央工作目录、`.git`、个人恢复包或个人 `006-skills` 整体发给同事；
- 同事电脑同时存在同名插件版和离线目录版；
- 更新时只替换部分 Skill，形成混合版本；
- 正在生产的项目未经兼容复核自动切换新版 Skill。

## 13. 项目结束

1. 用户明确要求后同步必要进度；
2. 按需做项目复盘，未授权则只分析不落盘；
3. 区分项目特有问题、可通用规则候选和模型能力边界；
4. 同事只提交反馈包，不直接修改中央系统；
5. 备份项目数据目录、最终 Prompt、可用镜头定位和必要授权材料；
6. 如果项目是 V01，按完成验收总表检查真实闭环并修复阻断项；
7. V01 完成后制作一份脱敏示范项目，加入后续同事培训包。
