# SKillXC 操作与同事交付手册 v0.1

适用范围：已有剧本或生产内容明确的真人写实项目；GPT Image 2 制作图片资产；Seedance 2.0 由用户在外部平台人工生成；终点为正式镜头 Prompt 与用户确认的可用镜头。

系统状态：结构化 Beta。系统结构、Skill、数据合同和交接规则已经建立；尚需通过 V01 真实项目端到端验证，才能称为“真人写实第一版生产闭环已验证”。

本手册供制片、导演、AI影视制作人员、数据记录人员和系统管理员使用。它解释“怎么操作”，不替代各 Skill 的专业规则；发生冲突时，以用户最新明确指令、项目当前有效数据、`production-router-handoff` 和责任 Skill 为准。

## 1. 三个直接答案

### 1.1 每个单项都要新开对话吗？

不需要。

推荐的新对话单位是：

`同一项目 + 同一责任 Skill + 同一对象范围 + 同一种写入权限`

例如：

- 同一人物的选脸、五视图、服装和剧情状态可以持续在该人物资产对话里迭代；正式登记另开登记对话。
- 同一场景的母图、空间圣经、预制视角和状态变体可以留在该场景生产对话；切换到另一场景时建议新开。
- 同一生成单元的 Prompt 多次返修可以留在原 Prompt 对话；正式 QC 记录和进度写入另开专用记录对话。

不要按“每问一句开一个对话”，也不要把整个项目从剧本到 QC 全塞进一个对话。

### 1.2 生产控制类与创作生产类要分开吗？

要分开，尤其是权威写入。

- **控制/记录对话**负责项目绑定、任务路由、事实索引、资产 ID、登记、控制卡生效、进度、审计和正式 QC 记录。
- **创作生产对话**负责风格方案、资产候选、场戏设计、分镜、Prompt 和返修方案。

创作对话可以提出“登记申请”“版本操作申请”或“进度同步包”，但不能直接写权威登记表、控制索引、进度表或正式 QC 表。控制对话只能核验和写入，不得趁机修改创作结果。

### 1.3 同事需要拿到什么？

至少需要：

1. SKillXC 仓库访问权限和固定版本/分支；
2. 本操作手册；
3. Codex Desktop、Python 3、Git，以及 GPT Image 2 / Seedance 2.0 的合法使用权限；
4. 正确安装到 Codex 的 30 个 Skill；
5. 一个项目启动包：剧本、项目名称/ID、项目数据目录、参考资料和审批负责人；
6. 对话命名规则、登记用语、交接方式和权限分工；
7. V01 完成后提供一份脱敏的示范项目数据，作为团队培训样例。

不要把个人 Codex 登录、API 密钥、个人项目数据、整个个人 `006-skills` 目录或历史聊天全文直接交给同事。

## 2. 系统的三层结构

### 2.1 中央 Skill 仓库

中央仓库保存 30 个 Skill、Profile 资料库、模板、Schema 和验证器。它不是具体影视项目目录。

- 普通同事在项目生产期间默认只读。
- 只有系统维护者审核后修改中央仓库。
- 中央 Skill 更新不会自动改写已有项目的控制卡版本。

### 2.2 项目数据目录

每个项目必须有独立的数据根目录和项目数据绑定卡。项目数据不能写进 SKillXC 仓库，也不能与其他项目共用表格。

默认数据结构是：

- Markdown 卡片：供人确认范围、结论、缺口和交接；
- CSV：保存多行权威记录；
- JSON Schema：检查表头和逐行结构；
- 数据校验报告：写在项目数据目录中。

结构检查通过不等于创作批准、资产登记、Prompt 放行或镜头可用。

### 2.3 Codex 对话

对话是工作台，不是唯一数据库。每个对话只读取当前任务所需的最小数据切片。

- 项目总控对话负责路由和恢复。
- 创作对话负责一个专业任务或对象范围。
- 严格记录对话负责权威写入。
- 跨对话使用短交接包，不靠同事凭记忆复述全部上下文。

## 3. 推荐的项目对话架构

### 3.1 每个项目必须保留的总控对话

建议命名：`【项目ID】-00-项目总控与路由`

职责：

- 使用 `$production-router-handoff`；
- 确认项目绑定、当前阶段、下一责任 Skill 和必要输入；
- 生成完整任务单及面向新对话的短交接包；
- 接收各专业对话的返回结果并决定下一阶段；
- 不替专业 Skill 直接创作，不代替专用记录对话写表。

项目暂停、换人或恢复时，先回到本对话确定当前有效任务版本。

### 3.2 建议长期保留的严格记录对话

这些对话必须与创作生产分开。小项目可每类保留一个；大项目可按批次新开，但必须使用短交接包和精确范围。

| 建议对话名 | 责任 Skill | 只负责 |
|---|---|---|
| `【项目ID】-01-项目绑定与资产登记` | `approval-asset-registry` | 项目绑定、正式资产登记、可调用映射、状态传播和回执 |
| `【项目ID】-02-创作控制版本` | `creative-control-versioning` | 风格四卡、表演母档、声音身份等项目控制卡的版本和生效状态 |
| `【项目ID】-03-生成与进度记录` | `generation-version-log` | Prompt/结果进度、生成批次、输入设置和用户失败描述 |
| `【项目ID】-04-正式审计记录` | `continuity-readiness-audit` | 用户明确要求保存的正式连续性/就绪审计 |
| `【项目ID】-05-正式QC记录` | `video-qc-review` | 用户明确要求保存的QCR根因、证据和返工路由 |

生成记录与正式 QC 不重复：前者保存“这次用什么生成、用户看到了什么”，后者保存“证据支持的根因和返工责任”。两类记录分别授权。

### 3.3 创作生产对话的建议拆分

#### 风格阶段

建议按部门分别建对话：

- 项目风格意图/导演风格；
- 美术与 LookDev；
- 全片摄影基线；
- 项目灯光基线；
- P0 风格测试与风格包放行。

摄影 Profile 只在全片摄影基线阶段常规询问一次。导演 Profile 在项目风格意图和场戏调度阶段分别询问；前一次选择不自动授权后一次。Prompt 和 QC 阶段不重新加载 Profile。

#### 资产阶段

按“一个正式对象或对象家族”建对话，不按每次生成建对话：

- `人物-角色名`：选脸、五视图、服装、剧情状态和人物—道具交互；
- `场景-场景名`：母图、空间圣经、其他视角、状态和光影状态；
- `道具/载具-对象名`；
- `生物/怪物-对象名`；
- `VFX-效果名`。

同一对象候选失败、参考调整和 Prompt 返修留在原创作对话。只有用户明确说“登记这张”“确认登记”等，才把登记申请交到严格登记对话。

#### 场戏阶段

建议按“场次 + 专业责任”拆分：

- 场戏节拍；
- 场戏表演；
- 导演调度；
- 场戏摄影约束；
- 镜头视觉设计；
- 剪辑与节奏；
- 逐镜摄影审核；
- 场戏声音；
- 正式视频 Prompt。

分镜链必须保持以下写入顺序：

`镜头视觉设计草案 → 剪辑提出修订 → 镜头视觉设计写回 → 摄影逐镜审核 → 镜头视觉设计写回技术修正 → 就绪检查 → 正式Prompt`

剪辑和摄影审核都不能直接改分镜表，分镜表只由 `shot-visual-design` 写入。

#### Prompt 与外部生成

一个 Prompt 对话建议只处理一个镜头组或一个清晰的生成批次范围。

- Prompt 对话建立 `VRM@版本` 和 `VPR@版本`；
- 用户人工复制到 Seedance 2.0；
- 系统不提交、查询或下载视频；
- “Prompt 没问题，我去生成”只表示 Prompt 放行；
- “镜头可用/成片可用”才表示生成结果可用。

#### QC

即时诊断可以按镜头组建独立 QC 对话，也可以在范围很小且对象唯一时由总路由转入；默认不落盘。正式保存 QC 必须进入专用 QC 记录对话。

## 4. 什么时候必须新开对话

满足以下任一条件时，新开或切换到专用对话：

1. 切换项目；
2. 进入项目绑定、正式登记、控制版本生效、进度/批次记录、正式审计或正式 QC；
3. 唯一责任 Skill 改变，且新 Skill 会写另一类权威成果；
4. 从一个人物/场景/道具切换到另一个独立对象；
5. 从一个场次切换到另一个场次，原对话上下文较重；
6. 导演、摄影、美术、剧作或剪辑 Profile 的责任阶段改变；
7. 当前对话已经混入大量无关候选、旧版本或其他项目内容；
8. 需要把任务交给另一位同事。

## 5. 什么时候不必新开对话

以下情况通常留在原对话：

- 同一资产候选的反复修改；
- 同一人物基础版到服装/剧情状态变体；
- 同一场景母图到同场景视角补充；
- 同一生成单元的 Prompt 表达返修；
- 完全相同 Prompt/参考/设置的原样重试；
- 同一责任 Skill 对上游换版做兼容复核；
- 用户给出方向后继续完成当前唯一任务。

如果变更会改变对象身份、责任 Skill、生成单元成员/顺序或权威写入目标，应先回总路由重新建任务或短交接包。

## 6. 新对话如何交接

不要把整个剧本、全部资产表、全部 Profile 和旧聊天全文复制到每个新对话。

在原对话中要求：

> 为当前任务生成短交接包和新对话激活指令。只包含项目ID、任务ID@版本、当前阶段、唯一责任Skill、完整任务单路径、最小数据切片、当前唯一目标、禁止事项和返回条件。

短交接包的核心格式：

```text
项目ID：
任务ID@任务单版本：
当前阶段：
唯一责任Skill：
完整任务单路径：
当前唯一目标：
最小数据切片（名称｜精确ID@版本｜项目内路径）：
用户尚需决定：
禁止事项：
返回条件：
```

把短交接包中的“短激活指令”复制到新对话。新对话先读完整任务单，再只读短包列出的最小数据；需要扩大范围时停止并返回总路由。

## 7. 真人写实项目标准操作流程

### 阶段 0｜安装与运行时验收

1. 安装并登录 Codex Desktop。
2. 安装 Git 和 Python 3。
3. 克隆 SKillXC 仓库到稳定位置。
4. 让系统管理员把仓库的 30 个 Skill 以目录链接接入 `%USERPROFILE%\.agents\skills`。
5. 完全退出并重启 Codex。
6. 新建测试对话，发送：

```text
请使用生产路由与交接，告诉我当前任务应进入哪个阶段；未经我确认不要调用其他 SKillXC Skill。
```

通过标准：Codex 能读取总路由并先询问项目绑定/当前阶段；不会自动加载其余专业 Skill。

### 阶段 1｜项目启动与绑定

在项目总控对话发送：

```text
使用 $production-router-handoff。我要启动一个已有剧本的真人写实项目。
项目名称：【填写】
建议项目ID：【填写或请系统提出】
项目数据根目录：【绝对路径】
剧本或生产内容：【附件/路径】
先只核对项目绑定与类别方向，未经我确认不要调用其他专业Skill。
```

总路由收集位置后，把项目绑定任务交专用绑定对话。项目绑定完成后返回绑定卡路径与版本。

### 阶段 2｜类别锁定

通过问答和参考图确定真人写实方向。类别锁定前不进入资产批量生产。

### 阶段 3｜剧本事实、资产拆解与需求计划

依次完成：

1. 剧本事实索引；
2. 候选资产拆解；
3. 正式资产 ID 预留；
4. 人物、场景、道具、特殊生物/怪物、VFX 等分类需求；
5. 父子依赖、生产顺序和缺口表。

预留 ID 不是正式资产；只有明确登记后才进入可调用表。

### 阶段 4｜风格锁定包

依次完成项目风格意图、美术、摄影、灯光四卡，必要时加载用户确认的 Profile 或专业顾问。完成 P0 测试并放行风格包后，才进入批量资产生产。

### 阶段 5｜资产生产与登记

每类资产进入对应创作对话。GPT Image 2 候选先由责任资产 Skill 验收；失败候选不登记。

只有下列明确措辞触发登记：

- “登记这张”；
- “确认登记”；
- “登记这段声音”；
- 其他对象、范围和动作同样明确的登记指令。

“可以”“不错”“继续”“按这个改”均不等于登记。

### 阶段 6｜场戏创作与分镜

在资产与必要表演母档就绪后，依次进入：场戏节拍、场戏表演、导演调度、场戏摄影约束、分镜草案、剪辑修订、摄影审核、声音适配。

如果构图、景别、机位或运镜不能传达情绪，返回 `shot-visual-design`；如果走位、遮挡、权力关系或轴线意图错误，返回 `directing-blocking`；不要让 Prompt 用形容词掩盖上游设计问题。

### 阶段 7｜就绪门与正式 Prompt

连续性/就绪检查通过后，`video-prompt-production` 建立：

- `VRM@版本`：媒体参考顺序、唯一用途和禁止继承；
- `VPR@版本`：单镜头或镜头组正式 Prompt。

每名人物实际只调用一张匹配当前服装/状态的五视图总览卡。Prompt 阶段不重新加载大师 Profile。

### 阶段 8｜外部生成、反馈与 QC

用户手工把正式 Prompt 和参考素材复制到 Seedance 2.0。

- Prompt 问题：回 `video-prompt-production`；
- 参考映射/负载问题：先改 VRM，再改 VPR；
- 上游设计问题：回唯一责任 Skill；
- 模型随机偏差：相同 VPR/VRM/设置原样重试，不升级版本；
- 需要系统诊断：调用 `video-qc-review`，默认不保存。

用户说“镜头可用”不要求上传视频。只有用户明确要求同步进度，才进入生成与进度记录对话。

## 8. 用户关键指令速查

| 用户原话类型 | 系统解释 |
|---|---|
| “登记这张/确认登记” | 触发正式资产登记申请 |
| “不登记，继续调整” | 保持候选身份，继续创作 |
| “Prompt 没问题，我去生成” | 当前 VPR 放行生成，不代表视频可用 |
| “镜头可用/成片可用” | 结果可用；不要求上传视频 |
| “同步本对话进度” | 生成进度同步包，交专用记录对话 |
| “保存这次生成批次/参数/参考” | 进入详细生成版本记录 |
| “保存本次QC/记录失败根因” | 进入正式 QCR 记录 |
| “复盘这个项目” | 默认只分析；另说“保存本次复盘”才落盘 |
| “继续/可以/不错” | 不自动登记、不自动放行Prompt、不自动判视频可用 |

## 9. 团队角色与权限建议

| 角色 | 建议权限 |
|---|---|
| 系统维护者 | 修改中央 Skill、验证、提交和发布版本 |
| 项目总控/制片 | 建项目、分配任务、批准阶段、维护总控对话 |
| 创作负责人 | 在指定专业对话生产候选和提交交接包，不写权威登记表 |
| 资产登记员 | 只按明确登记申请写正式资产、可调用表和回执 |
| 数据记录员 | 只按授权写控制版本、进度、生成批次、审计或QC记录 |
| 最终审批人 | 决定登记、Prompt放行、镜头可用和项目采用 |

小团队可以一人兼任多个角色，但仍要使用不同对话和不同写入模式，不能因为是同一人就跳过授权边界。

## 11. 当前团队分发的安装边界

因此：

- 可以立即向同事提供 GitHub 仓库和本手册；
- 由技术负责人按同事电脑的仓库位置建立 30 个 Skill 目录链接；
- 不要复制维护者完整 `006-skills` 目录，以免带出个人插件、私有 Skill、路径和完整性清单；
- 团队大规模使用前，建议另建只包含 SKillXC 的便携安装器，接受 `RepositoryRoot` 和 `UserHome` 参数，并提供安装、只检查和卸载/恢复边界。

便携安装器属于团队部署工具，不是影视生产闭环缺口；没有它仍可由管理员手工安装，但不适合让非技术同事自行操作。

## 12. 更新与版本管理

1. 生产项目固定引用具体 Skill/控制卡/Profile版本，不用“最新版”静默替换。
2. 中央仓库由维护者统一更新并通过测试后发布。
3. 同事拉取新版本后，如果只更新 Skill 正文，通过目录链接立即读取；入口元数据或安装结构改变时重启 Codex并做新对话验收。
4. 正在生产的项目不因中央更新自动改写项目数据；需要采用新规则时，由总路由建立兼容复核任务。
5. 项目数据必须单独备份；GitHub 仓库不能恢复具体项目素材、登记表或用户决策。

## 13. 常见错误

- 在一个对话里同时做资产设计和正式登记；
- 把“继续”当成登记、Prompt 放行或镜头可用；
- 新对话没有短交接包，靠复制旧聊天全文恢复；
- 每个对话加载全部 30 个 Skill 或全部 Profile；
- 把项目数据写入中央 Skill 仓库；
- 把失败候选登记成正式资产；
- 摄影审核或剪辑直接改分镜表；
- Prompt 阶段重新导演或重新选择 Profile；
- 只凭截图评价完整动作、声音或运镜；
- 把结构校验通过写成创作质量通过；
- 把维护者个人恢复目录直接复制给同事。

## 14. 项目结束

项目结束时：

1. 用户明确要求后同步必要进度；
2. 按需做项目复盘，未授权则只分析不落盘；
3. 区分项目特有问题、可通用规则候选和模型能力边界；
4. 未经维护审批，不自动把项目经验写成中央 Skill；
5. 备份项目数据目录、最终 Prompt、可用镜头定位和必要授权材料；
6. 如果项目是 V01，按完成验收总表检查真实闭环并修复阻断项。
